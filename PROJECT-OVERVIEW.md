# Accessible STEM — Project Overview

_Comprehensive write-up, written 2026-07-21 on branch `cm6-migration`. Companions: `HANDOFF.md` (session-to-session handoff, read that first when resuming work) and `FILE-MAP.md` (folder and line-number map; line numbers predate this branch and have drifted)._

## Purpose and audience

"Accessible STEM: A Toolkit for Instructor-Created Course Content" is an author-once / output-multiple publishing pipeline built at Harvard by Nicholas (GitHub `slowofmind`) for the Assistive Technology Center. Faculty-authored LaTeX course content (problem sets, handouts, exams) goes in; accessible HTML, DOCX, and eventually EPUB come out, with math accessibility as the core concern. End beneficiaries are ATC staff and the students they support — predominantly NVDA/JAWS/Kurzweil 3000 users, essentially all of whom rely on MathCAT for math. The entire tool is a single browser page, `index.html`, that runs Pandoc in-browser via WebAssembly and can route documents to two heavier remote engines (LaTeXML, LuaLaTeX) through GitHub Actions.

## Architecture in brief

Three engines behind one UI. **Pandoc** runs in-browser via WASM (offline, the default), through a patched Tweag wrapper that adds a synthetic `xform` device and compressed-wasm delivery (`pandoc-wasm.bin`, gzip + `DecompressionStream`; see HANDOFF for the portability notes). **LaTeXML** and **LuaLaTeX** run remotely on `ghcr.io/slowofmind/latexml-pipeline:latest` via GitHub Actions: `index.html` commits a `.tex` into an engine-specific input folder through the GitHub API, the workflow runs the container, output lands in the engine's output folder, and the page polls for it. A GitHub token embedded in `index.html` makes this work and is known security debt.

Math handling: HTML output defaults to static MathML produced client-side by the MathJax device pipeline (tex→MathML plus conditioning); DOCX math becomes OMML via `MML2OMML.XSL` in the browser's XSLTProcessor. That DOCX pipeline is itself a port of an earlier Node.js `tex2omml` tool from a July 5 session on the previous account. MuPDF (WASM) converts PDF images to SVG. Built-in Lua filters live inline in `index.html` as a `BUILT_IN_FILTERS` registry; the `filters/` folder holds reference copies only. SCORM packaging wraps HTML output in a minimal SCORM 2004 zip so MathJax can run inside Canvas.

The editor: on `main`, Ace; on the `cm6-migration` branch (all current work), CodeMirror 6 behind a small facade (`cm6-src/facade.js`, bundled by esbuild via `build-cm6.ps1` into `codemirror/cm6-editor.js`). The facade exposes editor primitives (text get/set, diagnostics, jump, highlight ranges, completion hooks); Pandoc-specific intelligence stays in `index.html` as data by design. Syntax highlighting uses the TeXlyre `codemirror-lang-latex` Lezer grammar (Overleaf lineage) with a CSS token palette in `index.html`.

## The cleanup system (state as of 2026-07-21)

The stack-based engine processes profiles of patterns against the LaTeX source: matched pairs ({prefix, anchor, suffix} opening/closing with stack counting on anchors, outermost-first, one nesting level per pass) and single strings (with optional regex and escape sequences), under three replacement modes — edit_tags (replace opening/closing tags; blank replacements are equivalent to removal and are the default everywhere), remove_tags, remove_all. An extension-only fourth mode, run_task, is recognized on import and safely no-ops.

Profiles follow a **workspace model**: the page loads with one empty profile ("My cleanup"), and every pattern source appends into the active profile through a single merge function with equivalence dedupe (pairs by opening triple, singles by find string), making any mix of sources in any order idempotent. The sources are: manual entry; hardcoded presets via an "Add preset patterns…" control (registry `PRESET_PROFILES` in `index.html`; append one object literal to add a preset); JSON import (accepts the VS Code extension's versioned envelope or a bare profile; same-major compatibility); and auto-populate from Pandoc conversion warnings (toggleable), which classifies `\begin{env}` warnings into environment pairs, `\cmd{...}` warnings into command pairs (dedupe by command name; robust to first-line truncation), suppresses redundant `\end{env}` entries, and falls back to single strings. Export downloads the active profile in the extension-compatible envelope; an optional failsafe checkbox also downloads the profile JSON alongside every converted-output download. A clear-all button resets the slate; restoring a saved profile exactly is clear-all + import.

Conversion-time integration: all three engines read their source through `getSourceForConversion()`, which (when the "Apply cleanup during conversion" checkbox is on) runs the active profile over a copy of the editor text — the editor itself is never modified — and injects a warning into the log that line numbers may not match the original. The line-number drift between cleaned text and editor content is a known, accepted problem.

## Roadmap and open questions

**Auto-populate differentiation.** Nicholas wants a way to distinguish auto-populated patterns from deliberate ones; options identified are a marker field (`autoAdded: true`, survives export, rendered as a badge, optionally with a clear-auto-added action), routing suggestions into a dedicated profile, or relying on the toggle alone. Decision deliberately deferred.

**Scope, revisited.** Two flagged items: JSON import currently appends patterns only and drops the file's profile-level scope; and the larger idea of multiple scopes within one profile (different pattern groups confined to different document sections), which would move scope from profile level toward pattern-group level — a data-model change with extension round-trip implications that needs a design conversation before code.

**Unified upload with auto-classification** (feasibility recorded 2026-07-21 in answer to a direct question): the UI currently has twenty-one separate file inputs, each feeding its own holding variable, but at conversion time `buildFiles()` flattens nearly everything into one virtual filesystem for Pandoc — so a single drop-zone upload that classifies files and dispatches into the existing per-category holdings is architecturally friendly, a routing layer rather than a rework. Classification is mostly by extension; the two real ambiguities are `.json` (cleanup profile vs CSL-JSON bibliography vs citation abbreviations — resolvable by content sniffing, since each has an unmistakable shape) and `.xml` (syntax definition vs EPUB metadata — root element). Multi-file `.tex` needs a main-document heuristic (`\documentclass`). The design work is a post-drop staging summary where the user can reassign before committing; the refactoring chore is extracting category handlers currently inlined in change listeners. Estimated one to two sessions when its turn comes.

**Editor backlog** (all on `cm6-migration`): punch up the syntax color palette (CSS-only, no rebuild); math-region background tint (facade change, its own checkpoint); the completion layer (hybrid: the grammar package's `latexCompletions` as base vocabulary in `index.html`, filtered against the Pandoc reader index; the facade mechanism is built and idle); prune the unused `@codemirror/legacy-modes` dependency on the next bundle touch.

**Standing items:** the pre-existing Ace `worker-html.js` error noted 2026-07-20 (obsolete if `main` adopts CM6, worth confirming); the embedded GitHub token security debt; extending the cleanup line-drift warning to the LaTeXML/LuaLaTeX log paths if wanted; possible timestamping of failsafe profile downloads; the eventual simplified-version planning Nicholas has flagged as a later phase.
