## What this project is

"Accessible STEM: A Toolkit for Instructor-Created Course Content" is an author-once / output-multiple publishing pipeline (Harvard; owner Nicholas, GitHub `slowofmind`). The whole tool is a single browser page, `index.html`, that turns faculty-authored LaTeX into accessible output (HTML / DOCX / EPUB) with strong math accessibility. It runs Pandoc entirely in the browser via WebAssembly, and can also route documents to two heavier engines — LaTeXML and LuaLaTeX — through GitHub Actions.

## Architecture

Three engines sit behind one UI.

- **Pandoc** — in-browser WASM, offline, the default. `pandoc.js` is a custom Tweag WASI wrapper carrying TWO local patches, each in a clearly fenced comment block: a synthetic `xform` DEVICE block near the top, and a WASM-LOADER block that fetches the gzipped `pandoc-wasm.bin` (~15 MB) instead of the raw `pandoc.wasm` (~56 MB), decompressing in the browser via `DecompressionStream` with a fallback to the raw wasm. If upstream `pandoc.js` is ever re-dropped in, BOTH patch blocks must be re-applied (upgrade procedure is in `FILE-MAP.md`).
- **LaTeXML** and **LuaLaTeX** — remote, via GitHub Actions on the Docker image `ghcr.io/slowofmind/latexml-pipeline:latest` (a `MODE` env var selects the engine). Flow: `index.html` commits a `.tex` to the engine's input folder via the GitHub API → the workflow triggers on push to that input path → the container runs → output is committed to the engine's output folder → `index.html` polls and fetches it. This relies on a GitHub token embedded in `index.html` (known security debt).

Built-in Lua filters are INLINE in `index.html` as `content:` strings in a `BUILT_IN_FILTERS` registry (default-lists ~L2776; resolve-image-paths ~L2830, which exists inline only, no loose file; embed-images ~L2921). The tool runs these inline copies — the loose `.lua` files in `filters/` are reference copies only.

Math device pipeline (`index.html` ~L4158–4300): `needsMathjaxDevice` / `ensureMathjaxDevice` import tex→MathML plus conditioning, load `MML2OMML.XSL` into an XSLTProcessor, register a device transform, and round-trip math through the synthetic `xform` virtual file. Defaults: HTML math is static MathML via the device; DOCX is OMML (via `MML2OMML.XSL`); MathJax-4 head-injection happens only for the `mathjax4` option. Do NOT change math conversion or output behavior unless Nicholas explicitly asks.

MuPDF (`index.html` ~L4205–4300): `loadMuPDF` + `convertPdfToSvg` (DocumentWriter `svg`) plus a pixmap/DPI path. The MuPDF trio self-relocates via relative imports, so moving that folder needs no edits.

## Recent work (2026-07-20) — compressed wasm delivery

**Problem:** the live GitHub Pages site took ~55 s to become ready, vs ~14 s for the public pandoc.org/app. DevTools measurement (`performance.getEntriesByType('resource')`) proved both apps use the identical ~57 MB `pandoc.wasm`; the difference was purely transport. Pandoc.org's host compresses it in transit (`Content-Encoding: zstd`, ~15.7 MB on the wire); our GitHub Pages instance serves it raw with no `Content-Encoding` — the CDN compresses small text assets (our `pandoc.js` went 9→3 KB) but skips the huge wasm.

**Fix:** ship our own compression. `compress-wasm.ps1` gzips `pandoc.wasm` → `pandoc-wasm.bin` (55.87 → 15.41 MB, round-trip SHA-256-verified) and the WASM-LOADER patch block in `pandoc.js` fetches the `.bin`, pipes it through `DecompressionStream('gzip')` wrapped in a `Response` with `Content-Type: application/wasm` (preserving streaming compilation), and falls back to raw `pandoc.wasm` on any failure. Result confirmed live: load time now matches the public app.

**Reusable technique + portability notes (read before compressing other wasm, or moving off GitHub Pages):**

- The same recipe applies to any large binary asset we add later (e.g. `mupdf-wasm.wasm`, ~10 MB — currently lazy-loaded, so lower priority): gzip it, give it a **non-`.gz` filename**, fetch + `DecompressionStream` in its loader.
- The `.bin` (not `.gz`) filename is load-bearing: traditionally configured servers (Apache is the classic case — plausible for an eventual Harvard-hosted deployment) see a `.gz` extension and add `Content-Encoding: gzip` themselves, so the browser transparently decompresses before our code runs, our explicit decompression then fails, and only the slow fallback saves us. A neutral extension makes the scheme portable across GitHub Pages (both flavors), Harvard web servers, and local test servers.
- When moving to any new host, verify with DevTools: the `pandoc-wasm.bin` request should transfer ~15.4 MB and the console should show no yellow `[pandoc.js]` fallback warning. If the host turns out to compress large files natively, the scheme still works — it's just redundant, not broken.
- `DecompressionStream` is baseline in all current browsers (Chrome/Edge 2020+, Firefox 2023+, Safari 16.4+); older browsers hit the raw-wasm fallback and simply load slowly.

## Milestone verified (2026-07-23 evening): minimal dual-mode sty — problems-only vs problems+solutions

Nicholas reframed: no divs needed per se; goal = sty definitions Pandoc expands/drops, single preamble line switches modes. Probes (%TEMP%\ministy) established the hard boundary first: **Pandoc has NO definition-level mechanism to discard an environment's content.** Three candidates probe-dead: (1) delimited macro `\long\def\solution#1\end{solution}{}` — CATASTROPHIC in Pandoc: silently swallows the ENTIRE document, exit 0, empty output (never use); (2) comment-aliasing — Pandoc's comment handler is locked to the literal name; (3) `\iffalse`/`\fi` in env bodies — Pandoc ignores them, content leaks UNLABELED (and it's broken in real LaTeX anyway: the skipper eats `\end{solution}`). Consequence: the undefined-env Div fallback is the ONLY sty-side way to keep hideable content identifiable; actual removal is preprocessing (strip blocks from source — correct for answer security) or a filter on the div.

Working design (`mini3.sty`, all quadrants verified): top-level `problem` = `{}{}`; `\problemsonly` = no-op marker (a directive the conversion tool can detect to auto-apply the solution-strip pattern); `\showsolutions` = `\renewenvironment{solution}{\par\textbf{Solution. }}{\par}` — **works in BOTH engines as a single document-preamble line** (Pandoc registers renews arriving via command expansion — probe-verified); `\DeclareOption{engine}{\let\solution=\comment ...}` + verbatim pkg = LaTeX-side default hiding, invisible to Pandoc. Results: pdflatex default = no solutions; pdflatex+`\showsolutions` = "Solution." lead-ins; pandoc+`\showsolutions` = clean bold-labeled solutions, no divs; pandoc default = `div.solution` (labeled) → one regex strip yields clean problems-only HTML.

**Scaled to the real worksheet (same evening):** test kit at `000-BBB...\handout-mini-test\` — `handout-mini.sty` v0.3 (ws2-2 vocabulary: probonly/solonly/note/pspace/nstretch/plainitem/circleitem/maybecircle/uline + standalone shims + problemonly; fitb/cfitb/mc/tf deliberately absent), `plotstyle.sty` copy, `ws2-2-problems.tex` / `ws2-2-solutions.tex` (differ by the one `\showsolutions` line), `README-test.md`. ## Verified design option (2026-07-23): SINGLE-FILE specialsty via \DeclareOption quarantine

Probe-verified on both engines (%TEMP%\onesty): a one-file dual-engine sty works. Structure: top-level = Pandoc-facing simple definitions; `\DeclareOption{engine}{ real implementations }` + `\ExecuteOptions{engine}\ProcessOptions` = LaTeX-only layer (Pandoc swallows option bodies unparsed; pdflatex executed them and they override — PDF showed engine tabular wrapping while Pandoc converted cleanly even with a split-tabular definition inside the block). Emergent placement rule from this week's corrections: **commands top-level** (must be expandable or Pandoc destroys their arguments), **environments engine-only** (top-level env definitions — even empty — destroy the Div class; absence preserves content + class via fallback). Caveats: option bodies must be brace-balanced (Pandoc grabs them as one group); two-layer design retains the advantage that its engine can be `\RequirePackage{handout}` (faculty file untouched) and is never read at all. ## Corrections to the record (2026-07-23, probe-verified) — unknown commands, DeclareOption, hazard list, page-breaking

Three beliefs steering this project were probe-tested after Nicholas challenged them, and CORRECTED:

1. **Unknown commands do NOT leak their arguments.** Pandoc's unrecognized-command fallback consumes the command AND its following `[opt]`/`{...}` groups together and drops them all (verified: `\probonly{X}\solonly{Y}` vanish entirely; a 4-argument unknown command swallowed all four groups). The prior "brace groups leak as content" belief is wrong FOR ARGUMENT POSITION; only **bare** groups (no command in front) pass content through (that's the `{4}` leak after a failed env parse). Corollary (probe-verified same day): an UNKNOWN ENVIRONMENT's arguments are bare groups and DO leak — `\begin{mc}{c}` under the Div fallback emits `<span>c</span>`, i.e. the answer key leaks into problems HTML for `mc`/`tf`; needs a cleanup pattern (strip the arg) or filter (drop the leading unclassed Span in div.mc/div.tf). Consequence: unknown conditional COMMANDS silently DESTROY content (`\probonly{...}` problems text lost without the sty) — the pro-environment argument stands, but the failure mode is loss, not leakage. Also: `\ifSubfilesClassLoaded{...}{...}` is harmless (earlier leak warning withdrawn).
2. **`\DeclareOption` bodies are swallowed whole, never parsed** — there is no "every mode block executes / last definition wins." Only TOP-LEVEL definitions register, so with the sty parsed, Pandoc always behaves as handout.sty's DEFAULT (problems) mode, deterministically: `\probonly`=keep, `\solonly`=discard, problem env = space-reserving definition.
3. **The live split-environment hazard list shrinks**: `grading`/`workshop`/`wsplan` redefinitions live inside option blocks → never registered → NOT hazards (top-level selves are inert comment-aliases → Div fallback). Live hazards (top-level + split-body + used): workbook.sty `imagetable`, `enumeratecols`; handout.sty `mc` (l.180), `tf` (l.206), `objectives` (l.402). 22a `logicpuzzle.sty` still needs a top-level check. (`\NewEnviron`-defined environments are structurally immune to the split pathology — one body — and Pandoc drops `\NewEnviron` anyway.)
4. **LaTeX-side correction (not Pandoc):** the claim "commands can't contain page-spanning content" was wrong. An (unstarred, hence `\long`) `\newcommand` argument is re-injected as tokens and page-breaks normally; unbreakability comes from BOXING, which is orthogonal to the command/environment distinction (minipage is an unbreakable ENVIRONMENT; `\parbox` its command twin). Genuine environment-only powers: verbatim/catcode immunity (command args are pre-tokenized), comment-style untokenized skipping (needs an end delimiter), no-absorption memory/error hygiene for huge bodies.

## Recent work (2026-07-22) — multi-file include support (nested virtual FS)

**Problem:** converting the Math Ma Fall 2025 workbook (`main.tex` + 33 `\subfile`d worksheets, uploaded as a directory) failed with `Could not load include file ws/1/ws1-1.tex` for every worksheet. Same failure reproduced with a clean 5-file test kit (`000 - Broad range of Math samples\include-test\`), on pandoc.org/app, and NOT on native CLI — CLI produced correct chunkedhtml with working cross-file `\ref` links.

**Root cause (two independent defects, both now fixed on `cm6-migration`):**

1. **Flat virtual filesystem (upstream pandoc-wasm bug).** `pandoc.js`'s `addFile` did `fileSystem.set(filename, file)` on a single root Map, so `ws/1/x.tex` became one root entry whose *name* contains slashes. The WASI shim (`@bjorn3/browser_wasi_shim@0.3.0`) resolves paths component-by-component through nested `Directory` objects, so every multi-component open returned ENOENT. Fix: NESTED-FS patch block in `pandoc.js` (third local patch, same banner convention as DEVICE and WASM-LOADER) — `addFile` now splits on `/` and builds nested `Directory` nodes; `getFileEntry` replaces the two `fileSystem.get()` output lookups in `convert()`. Verified against shim 0.3.0 source: `Directory.contents` is a Map; the shim rejects absolute paths, so relative names are the supported form.
2. **Wrapper-folder mismatch.** Browser directory uploads keep the selected folder's own name as the first `webkitRelativePath` component (`include-test/ws/1/x.tex`) while the document says `ws/1/x`. Fix in `index.html`: the directory-upload handler now collects top-level folder names and auto-appends them to the Media tab's Resource path field (visible/editable); pandoc searches the resource path when resolving includes and images. Also fixed: `resource-path` was passed to `convert()` as a CLI-style colon string; the defaults format wants a list, so it's now split on `[;:]` into an array.

**Related conversion findings (chunkedhtml, from the include-test experiments):** `-t chunkedhtml --split-level=2` gives index + chapter pages + one page per worksheet with prev/next/up nav and cross-chunk `\ref` link rewriting. **Follow-up (same day) — the split-environment `.sty` hazard.** Converting the real Ma workbook WITH its sty files uploaded produced a hard abort: `Error at "ws/1/ws1-3.tex" (line 139, column 18): expecting \end{document}`. CLI bisection (shadow-sty variants, then safe-point document cuts at blank/brace-balanced lines with computed enumerate closers) established three things. (1) **Pandoc's reported error position can be hundreds of lines from the true cause** — the real failure is the `\begin{imagetable}{4}{\Alph}` usage at lines 538–555; "line 139" is a Parsec backtracking artifact. Naive truncation bisects chase this ghost and also self-inflict artificial failures when cuts land mid-`\note{...}` or unbalance enumerates (an *extra* `\end{enumerate}` is itself a distinct fatal mode). Always cut at brace-balanced blank lines with only enumerate/document open, appending depth-computed closers.
